# How LeaseResources got here

LeaseResources was designed, built and repaired by Claude Code sessions on the house machines between 2026-09-27 and 2026-11-15, at the user's direction. This account is drawn from the archived transcripts of those sessions, the service's own deployment log and its decision files. Times are UTC.

## At a glance

| Period | What happened |
|---|---|
| 2026-09-27 | Designed in the morning, built by a sub-agent in about half an hour, and installed on six machines within a day, with five rounds of Windows fixes in between. |
| 2026-09-28 to 10-04 | Logs and state off the synced folder; desk names and mail routing; the waiter, so sessions stop depending on mail; faster compliance scans; the macOS background throttle found. |
| 2026-10-08 to 10-27 | psutil's shifting create times on the Mac; hot-swapped disks and disk attribution on Windows; report names in UTC. |
| 2026-10-31 to 11-13 | Less traffic on the synced folder (reports on change, beats, fixed slots); a switch for moving reports to a Tailscale postman; disk maps that fail loudly; a watchdog for a dispatcher that cannot recover by itself, and stack dumps from such a hang; queued leases that fit overtake a blocked head; extensions tested only where they raise, and per-process rates over each process's own readings; disk needs capped instead of refused, and disk capacities from benchmarks; test runs that may overlap. |
| 2026-11-15 | Stack dumps only from a stalled dispatcher, so they no longer crash the Windows dispatchers. |
| 2026-11-18 | Headroom per resource: a whole disk, link or GPU can be leased; cpu 0.95; ram and GPU memory keep 0.85. |
| 2026-11-19 | Lease and trial ids are claimed atomically, so requests made in the same millisecond never share one. |
| 2026-11-20 | A running lease is credited with its disk's traffic up to its need, so writes draining from the page cache no longer count as unleased. Starts and ends are noticed every second, so a chain of short jobs no longer idles up to 5 s between them. |

## The design: 2026-09-27

**11:22 to 12:47, Altiplano: a self-review becomes a service.** LeaseResources came out of a self-improvement session in which the user asked Claude to read the past 30 days of conversations and find what better tooling could fix. Two findings were about long work: long jobs died with the session that started them and stalled unseen (one run had been dead for 11 hours before anyone noticed), and three machines shared one GPU on Mistral with nothing coordinating access. The first proposal leaned on the `claude` command-line tool for unattended runs. The user answered "I'm trying to get rid of claude-CLI. Please reconsider all open possibilities with that constraint." and pointed at the house's mail service for inspiration. The second draft was still built around the bottlenecks seen so far, and the user widened it: "I would prefer to not focus on those, because once we do, a different bottleneck will emerge that's currently out of scope (e.g. RAM, or network traffic)." His proposal became the design: "we give agents a durable tool to supervise how many computing resources they're currently using, mandate a trial run that's guaranteed to be concluded in <10 seconds, and if they want to launch anything longer, they have to request longer-duration resource use from a resource dispatcher that runs on each machine."

**12:47: guidance, measured.** The sketch made every resource a named dimension with a capacity and a measured use, so that a new bottleneck is one new probe, and gave the dispatcher one admission rule for every dimension. Claude recommended enforcing the mandate with a hook that cuts every unleased shell command at 10 seconds, since the self-review had shown prose mandates failing. The user chose otherwise: "OK great! Let's go with b) for now." The mandate would start as guidance, the dispatcher would count how often sessions comply, and a hard cap would follow only if they did not.

**12:52 to 13:25: the build.** A sub-agent built the service in about half an hour: the `res` tool, the dispatcher, a keeper that restarts it whenever its code changes, the job runner, the probes, installers for macOS and Windows, and a sandbox suite of 12 tests. The suite measured the core promises: a runaway tree of nine processes, including a `setsid` child and an orphaned grandchild, killed after 10.27 s with nothing left; a second GPU lease queued and granted a second after the first ended; a RAM overrun reported in 2.3 s without killing the job; a leased job surviving SIGKILL of its starting shell's process group and a dispatcher restart. It went live on Altiplano at 13:16. The first completion mail reported zero peak use for a job that plainly used memory, because peaks reached the lease file only once a minute and the finish step re-read the file; that was fixed at 13:18. The build agent also asked whether a session's own local `res run` should be held to the rule that a leased program must be a Python or PowerShell script under an allowed folder. The rule exists because a synced file that can start programs on any machine is a remote-execution channel, but a direct local run never passes through that channel. The user answered "Yes, good intuition - a local session is allowed to bypass.", and by 13:25 local runs could start any program while orders planted in the synced folder still did not run.

## The rollout: 2026-09-27 and 28

**13:53 to 14:49, Sandbank.** The guidance paragraph went into the house's long-jobs habit file, and install mails went to the five other machines. Sandbank's session refused to install a persistent service on the strength of a mail from another Claude, and went ahead only after the user approved it there himself. On this Intel Mac the battery found that `res mine` showed 0.00 cores for a busy process (psutil's first `cpu_percent` call always reads zero) and that the compliance record missed jobs backgrounded out of their tool shell.

**21:58 to 23:44, Moosfels: five rounds on Windows.** Windows was where the bottlenecks were and where nothing had run yet. Moosfels reported that the 10-second trial had run for 60 seconds and then hung. The fixes were made on Altiplano by reading, since Windows cannot run on a Mac, and each reached Moosfels through the sync and restarted its dispatcher by itself, which made the rounds fast: 22:22, 22:40, 23:03, 23:32 and 23:44. Round 1 moved the kill onto a timer thread and started the command suspended inside a Job Object with kill-on-close. Round 2 was forced by a finding about the suite itself: its keeper test touched the synced `probes.py`, so every run of the suite restarted the production dispatcher on every machine; from then on the suite runs a private copy of the code. Rounds 3 to 5 were about the compliance record. Every Bash-tool command had been missed, because the session's persistent Git Bash shells had themselves been recorded as escaped processes and swallowed everything below them; snapshots of the process table showed the real shape, and the detector was rebuilt around the nearest tool shell on each chain. A scan every 60 seconds could miss a 150-second command, so scans went to every 5 seconds. In round 4 lease requests went unanswered because the scan ran in the dispatcher's main loop and asked ClaudeMail for a desk through a subprocess for each new record; in its own thread, answers came in 0.5 s instead of 8.2 s. After round 5 Moosfels passed the whole Windows battery.

**23:18 to 02:01, Mistral, Teppich and Stahlwerk.** Mistral, Teppich and Stahlwerk installed by their own sessions. Teppich passed everything on the first try, and its notes led to `res trial` exiting with 3 when it had to cut the command off, and to rates being taken from a process's second sample, after a completion mail claimed 1.45 cores for a sleeping counter. Stahlwerk found the most serious bug of the day. The suite put its scratch folder in the temp folder, which on the Windows machines is a RAM disk of about 5 GB where Claude also writes its tool output, and a rate test wrote for five seconds bounded by time rather than size. The disk filled, and every Claude tool call failed until the user deleted the folder by hand; on Altiplano the same writer had quietly left 124 GB over the day. Scratch moved to a local cache folder, every writer was bounded by size, and the audit extended to the service itself, which wrote leased-job logs without any limit and into the synced folder. Stahlwerk also found that stopping a waiting `res run --wait` killed its job, because the waiting process was the job's parent; from 02:01 every runner starts through a short-lived intermediate that exits at once.

**2026-09-28, 11:24 to 11:57, off the synced folder.** A new house rule said that files a program keeps rewriting do not belong in the synced folder, where they cause conflict copies. Lease records were written by the requesting machine and rewritten by the target's dispatcher, and the heartbeat was rewritten every cycle. Logs and state moved to machine-local folders, and what another machine must read became write-once. Mistral's report the same morning led to the last fixes of the rollout: a process reading the archive disk while working on the system disk had its bytes put on the system disk, a trial on Mistral picked up the GPU work of the model server beside it, and two requests in the same second got the same id.

## Desks, the waiter and the throttle: 2026-09-29 to 10-04

**2026-09-29 and 30, desks and mail.** The Mac installer learned to refuse running as root, after Sandbank showed that under `sudo` launchctl finds no login domain and silently keeps the old job. A session working in a desk whose name contains spaces found its lease mail going to the machine's General desk, because `owner_desk()` split the output of `mail.py whoami` on whitespace. ClaudeMail gained a machine-readable `whoami --desk`. Asked whether mail to an unknown desk should fall back quietly, the user answered "Open question: warn the sender." The same afternoon, sibling sessions of one desk were taking each other's lease notices, and lease mail began to name the requesting session.

**2026-10-01, 17:13, the waiter.** Mail had turned out to be an indirect way to tell a session that its job had ended, so the session now waits on the lease itself. `res run --wait` and the new `res wait` register as the lease's waiter; while it lives, the dispatcher writes each notice as a file that the waiter prints and deletes, claimed by rename so a notice is printed or mailed but not both. An overrun, a run past its duration or a stall ends the wait with exit code 75 while the job carries on; the finish ends it with the job's own exit code. A session that runs the waiter as a background command is woken by its exit, so it never polls. A verifier's review found that a damaged notice file would have stopped metering and the queue in every tick, fixed at 17:30.

**2026-10-03, Moosfels: echo encoding and a test that could only pass unleased.** `res trial` died with `UnicodeEncodeError` after its command had finished: the output tail held a character the cp1252 console could not encode, and the traceback swallowed the profile. One call at the start of `main()` now makes both output streams escape what they cannot encode. Running the suite then showed that one test failed whenever the suite itself ran under a lease, as the house rule requires: every leased job inherits `LEASERES_LEASE`, the sandbox passed it on to the stand-in Claude process, and the detector rightly passes over a process that carries a lease. The sandbox now drops `LEASERES_*` as well as `CLAUDE*` variables. Later that night the dispatcher's third of a core on Moosfels was measured with the brief "first measure, do not assume": the steady cost was the command line of 152 processes that refuse access, about 11.6 ms each, because psutil never caches it. The scan now remembers such a refusal for the life of the process, and its cost fell from about 2 s to 0.10 s.

**2026-10-04, the throttle on the Mac.** Suites that a Mac's dispatcher started failed tests that passed when a session started them. The cause was the LaunchAgent's `ProcessType Background`: macOS runs the dispatcher and everything it starts at background priority, and one Python thread ran 5 to 6 times slower. Five tests were fixed, and changing the process type, a question of how much a remote job may take from the laptop the user is working on, went to him as an open decision. On the way, the disk map learned to skip ignored mounts before asking `diskutil` about them, and a first meter on Altiplano fell from 4.1 s to about 0.4 s.

The versions between 2026-09-30 15:42 and 2026-10-03 23:34 could not be recovered one by one: the waiter was built in a scratch copy that no longer exists. In the repository those changes arrive together in one commit.

## Clocks, disks and time zones: 2026-10-08 to 10-27

**2026-10-08, 21:31, Altiplano: jobs reported lost.** Seven leases had been reported lost within seconds of their start, while every one of them ran on and ended with exit code 0. The cause was in psutil 7.1 and later on macOS: it adds to every create time the distance the system's boot time has moved since psutil was imported, and macOS moves its boot time whenever the clock is corrected. After days of running, the dispatcher read every new runner 2 s later than the runner read itself, past the 1 s it allowed. A restart resets the shift, which is why the fault appeared only days after a start and never on Windows. The fix subtracts the present shift, through psutil's own private function. At 23:55 the same shift was found splitting one long unleased command into two records at a restart, and the compliance scan on the Macs now keys processes by the kernel's create time.

**2026-10-26, Pulvermaar and Mistral: a seventh machine, and disks on Windows.** Pulvermaar joined the house. On Mistral a session moving data between drives got six false overrun notices in two days, and every request naming the two drives in its hot-swap bays was answered "no such disk here", while `res trial` measured them fine. The dispatcher had built its disk list once, before the drives went in, and a trial builds a new meter, which is why trials saw them. And on Windows, where open files were not read, a job's bytes were spread over every disk by what each moved, so a reader was blamed for disks other programs kept busy. Every sample now compares a cheap disk signature and rebuilds the dimensions when it changes, Windows reads open files again, and each process's bytes go only to the disks it has files open on. Right after the deploy, Altiplano's report showed three new disks, Xcode simulator runtimes, and their mount prefix joined the skip list.

**2026-10-27, 05:02, Pulvermaar: report names in UTC.** Report files were named by local time and the two newest by name were kept. When Pulvermaar's local clock went back several hours, every new report sorted as the oldest and was deleted at once, and readers kept seeing the last report from before. Names now carry UTC.

## Less traffic, louder failures: 2026-10-31 to 11-13

**2026-10-31, fewer reports, no fallbacks.** The report folders held 39,698 to 47,106 deleted-file entries each, and every Resilio peer keeps and walks them for good. Reports went out on change and at least every 10 minutes instead of every minute. Two fallbacks also went: a missing owner desk no longer falls back to the machine's general desk, which under the house's new mail routing would have opened a new session for every notice. The session that prepared the change was not allowed to copy it into this folder, and the user copied it into place himself.

**2026-11-01, a small beat.** At idle a 33.6 KB report still went out every 10 minutes that differed only in its timestamp and compliance count. The report is now written only on change, and a separate beat of about 1 KB carries the freshness. The one-second tick stopped re-parsing every lease record, and the compliance summary reads only what was appended since its last pass.

**2026-11-10, fixed slots and the postman switch.** Together with the reports of ClaudeMail and the supervisors, deleted report files had piled up some 80,000 records and stalled one machine's sync for 12 days in October. Reports and beats now overwrite the oldest of five fixed slot files, and readers pick the newest by the time inside, never by name. The same day the user chose to move the house's machine-to-machine traffic off the synced folder onto a listener on every machine over Tailscale ("listeners on seven machines - it would mean decentralization and robustness to outages"), and a `reports_via` setting was deployed as `"files"`, ready to be flipped for the whole fleet at once.

**2026-11-11, 03:14, Sandbank: disk dimensions lost under load.** Sandbank's dispatcher refused lease requests, saying it had no disk dimension, while `res now` showed the disk. Overloaded, `diskutil info` had been killed by its timeout; the failure became a missing disk in a cached map, and the probe re-maps only when the disks change, so it never asked again. `diskutil` failures now raise so nothing incomplete is cached, a running probe keeps the disks it had while a re-map fails, and retries are bounded to one a minute so a slow `diskutil` cannot stall the dispatcher.

**2026-11-13, 00:24, Mistral: a dispatcher that could not recover.** On 2026-11-12 Mistral's dispatcher answered nothing for 11 hours while its compliance thread kept logging, so the log looked alive and the keeper waited. `py-spy` showed the main thread stuck in `threading.Thread.start` inside a `subprocess.run` with a 10 s timeout. The inferred cause: psutil 7.2.2's Windows `open_files()` kills its per-handle helper threads with `TerminateThread`, and a thread killed while it holds the Windows loader lock leaves that lock held, after which no new thread can start in the process. A test script that leaves the lock held hangs `Thread.start`, `subprocess.run` and `os._exit` alike. Because such a process cannot rescue itself, the keeper now kills the dispatcher from outside after 10 minutes without a heartbeat and starts a new one, leaving leased jobs alone. Building it turned up one more trap: on Windows the keeper's child is the venv's launcher, not the dispatcher, which would have killed a healthy dispatcher every 10 minutes.

**2026-11-13, 12:43, Mistral: a queue that overtakes.** A disk-to-disk copy on Mistral asked for a 16-hour lease at 20:15 the day before and waited 15 h 41 min at the head of the queue. It needed 101 MB/s on each of two disks, and unleased traffic on exactly those disks kept them over the limit all night, first on a new disk whose learned capacity was still only 153 MB/s, later at over 200 MB/s on both. That traffic was most likely the copy itself, started without its lease. Its owner released the lease a minute after the grant. Under first come, first served, three small leases behind it waited between 13 h 41 min and 14 h 33 min while at least 24 of 32 cores were free: a 0.5-core database check, a 1-core count and a short photo job on another disk. The first two then finished in 74 and 107 seconds. The user approved two changes the same morning. First, a queued lease is now granted when it fits with every lease ahead of it counted as if granted. It can overtake a blocked head but never takes what the head needs, so on the head's blocked dimension nothing overtakes. Second, a lease still queued after 30 minutes gets one notice: what blocks it, the long commands of Claude sessions running there without a lease, and how to give it back. The report now carries the dimension each queued lease waits for.

**2026-11-13, 19:38, Stahlwerk: a hang leaves its stack.** On 2026-11-12 at 03:53, eight hours before the Mistral hang began, the dispatcher on Stahlwerk had stopped its main loop for 7.5 hours, right after a leased job that started some 20,000 short `ffprobe` processes had ended, while its compliance thread logged on. Its keeper predated the watchdog, so the user ended it by hand, and nothing showed where it had hung. That it was the same loader-lock hang is likely but not shown: a compliance scan during the first run of the same job took 105 s, the sign of the main thread holding the GIL in `open_files()` on that job's processes. So the next hang must leave a stack. The dispatcher now arms Python's `faulthandler` once at start, with `repeat`, so its own watchdog thread dumps every thread's stack into a local file every 150 s, and each healthy pass of the main loop empties the file. After a hang the file holds only the dumps written since the last healthy pass, and the keeper names the file when it kills the dispatcher. Arming it again on every pass would start a new thread each time, which is just what a held loader lock forbids; a thread started before still dumps, as a script that takes the loader lock and never releases it showed. `py-spy`, run by the keeper at the kill, was weighed instead: it would show native frames too, but it needs root on macOS and is not installed everywhere.

**2026-11-13, Mistral: an extension refused by what the lease already held.** A bit-flip search leased 16 cores, 260 MB/s on an NVMe disk and 180 MB/s on each of two hard disks. When it read the NVMe at 709 MB/s, its owner asked `res extend --need` for 900 MB/s there, and was refused on one of the hard disks, a disk the request did not name: "unleased 13.1 MB/s + leased 0 B/s + this 180.0 MB/s > 186.3 MB/s allowed". The extend path tested the whole merged need again, with the lease's unchanged 180 MB/s as "this" and 13 MB/s on that disk that the meter had not put on the lease as "unleased", so a lease that declared close to a disk's limit could never be extended in any other dimension. An extension now tests only the dimensions it raises, and a cut is always accepted. The same job read 43.5 and then 114.7 cores on a 32-thread machine, most likely like this (the job was not run again; the mechanism was reproduced in a test). Each search started a fresh pool of 32 workers; their first sample, which has no rate yet, was quick, and in the next one each worker waited behind the open-files reads of the workers before it, up to 0.4 s each. Rates divided by the time between two sample starts, so the late workers' extra seconds of cpu fell into too short a span. Rates now span each process's own two readings; four one-core processes behind 0.3 s of open-files each read 8.15 cores before and 4.0 after.

**2026-11-14, 13:00, all machines: disk leases near a disk's real speed.** A drive on Teppich that runs up to 220 MB/s could not be leased above 135. Two things stood in the way. A request built from a trial asks for the trial's peak plus 25 %, and a job that runs a disk flat out peaks at about the disk's own speed, so it always asked for more than the 85 % the dispatcher allows, and was refused. And a disk's capacity was learned: it started at 150 MB/s and rose to the highest 5-second rate ever seen, which on one disk meant 150 for days and then 317, more than the drive can do. Now a disk or network need above the limit is cut to the limit and granted, because given less of a disk a job only runs slower; cpu, memory and GPU stay refused, where a job could fail. A capped lease is held to the full capacity, so the headroom absorbs traffic nobody leased. And on Windows each disk's capacity comes from the outer-track read of its newest benchmark in the drive archive, matched by serial number; a disk without one keeps a learned value, and each disk now says where its capacity came from.

**2026-11-14, Altiplano: test runs that overlap.** Every run of the sandbox suite began by deleting all the scratch folders it found, on the assumption that only a killed run leaves one behind. A 4-second run of one test class, started while a full run was going, therefore deleted the full run's copy of the code and its sandboxes, and the full run failed in 19 unrelated tests. Each run's folder now carries its host name, process id and create time in its name, made in a single step, and a starting run deletes only folders whose process has ended (a reused process id has a later create time), after killing anything still running from them.

**2026-11-15, 14:08, all machines: stack dumps only from a stalled dispatcher.** From the day the stack dumps came in, the Windows dispatchers died with an access violation in `python311.dll` every few hours: five times on one machine in a day and a half, once each on two others, after a month without one. The service supervisor on the first machine found that each fault lay in the interpreter's traceback-dump code and that each crashed process had left its stack file behind, and asked for a fix by mail. `faulthandler.dump_traceback_later` dumps from a C thread that reads the other threads' frames without the GIL while they run, and it had been doing that every 150 s on every healthy dispatcher; now and then it met a frame being freed. The dispatcher now starts a plain Python thread of its own once, at start, which dumps with `faulthandler.dump_traceback` while holding the GIL, and only once no pass of the main loop has come for 150 s. It keeps the property the first version was built for, since a thread started before a held loader lock still runs, which a script holding that lock confirmed on Windows again. The cost is that a hang that holds the GIL shows no stack until it lets go. A stress run that dumped every 2 ms for three minutes did not crash with either method, so the fix rests on where the crashes were, not on a reproduction.

**2026-11-18, all machines: a whole disk, link or GPU can be leased.** Every dimension had shared one headroom of 0.85, so no lease could ask for a disk's full speed, and a GPU job that needed the whole card was refused. The headroom only has to guard what fails when overcommitted. A disk, a network link or a GPU's compute shared too thinly only makes a job slower, so their headroom is now 1.0; cpu, also only slower but shared with the person at the desktop, went to 0.95; ram and GPU memory, where a job can crash, stay at 0.85. The per-dimension setting had existed since the start but was empty. A machine's own `headroom_by_dimension` used to replace the default one whole, so a machine raising only its GPU memory would have dropped the new disk entry; machine settings that are objects are now merged into the defaults key by key.

**2026-11-19, 17:30, Mistral: two requests, one id.** Four processes of one job each ran `res request` within the same few milliseconds and got back three ids; two of them held the same lease. The first run order on it was accepted and the second refused, since a lease takes one run order, so one build never ran. An id is the time to the millisecond plus the machine, and a suffix is added when the id is taken, but "taken" was checked against the lease folder and a shared list of sent ids, and nothing stopped two processes from both seeing an id as free before either wrote it. The same gap had been narrowed once before, from seconds to milliseconds, on 2026-09-28. Now each id is claimed by creating a folder of its name in the machine's local state, which the file system lets only one process do; a process that loses moves on to the next suffix. Claims are kept for a day, so a clock set back cannot hand out an id again. Eight processes asking for 200 ids each at once got 1,600 distinct ids, 310 of them by a suffix. A new test makes 200 ids from eight threads with the clock stopped; the code before fails it.

**2026-11-20, 01:43, all machines: a copy's own writes counted as nobody's.** A job that copied disk images one after another, each from a RAM disk to a hard disk under its own lease, found that the next copy waited about 20 s after each one ended, with a waiting line like "unleased 126.3 MB/s + leased 0 B/s" although nothing else was writing to the disk. The job's owner guessed that the meter kept counting a finished lease's bytes as unleased for a while afterwards. A trace once a second showed that the cause came earlier. Each copy wrote its 2.5 to 3.5 GB into the page cache in under a second and then waited in `fsync` for 15 s while the disk drained the cache at 205 to 218 MB/s, and through all that time the process's own byte counters did not move. The meter credits a lease only with what its processes are seen moving, so none of the 170 copies leased that night had any disk use recorded, and every copy counted as unleased traffic in full. The 30-second average then carried those bytes past the copy's end. A running lease is now credited with its disk's traffic up to its need, as it already was on a network link. That cannot overbook the disk, because the full need is counted as granted anyway. Right after a 16-second copy ended, the disk then read 35 MB/s unleased instead of 114 to 126. The rest is the copy writing faster than the 170 MB/s it had asked for.

**2026-11-20, all machines: the next job a second after the last.** The same chain of copies showed 5 to 6 s between a lease being granted and its job being logged as running, and as much between one short copy's end and the next grant. The job itself started at the grant; the dispatcher only noticed starts and ends, and served the queue, once per 5-second sample, so a chain of 1-second copies stood idle most of the time. The user's word on it: "I think we can dial it down to one second." Starts, ends and the queue now run every tick (1 s), while metering, overrun counting and the report stay at 5 s, since a sample reads the open files of every process that moved bytes. In a test with 1-second jobs chained on one dimension, the next grant came 0 s after each end (whole-second stamps), against 4 s with the code before.

## Lessons learned

**Measuring resources**

- Treat every resource alike. The bottlenecks seen at the start (a spinning disk, two GPUs, CPU) were not the ones that later mattered most; one rule for every dimension meant no redesign when they changed.
- Measure, don't declare. Admission counts what the machine is using, so services that never ask for a lease are still counted.
- Spreading a measurement by a guess is worse than leaving it unknown. Bytes spread over all disks blamed a reader for disks it never touched and ended its waiter six times; attributing bytes only to disks a process has files open on fixed it.
- Measure before optimising. A first-pass timing blamed the parent lookup; repeated passes showed the cost was an uncached command line for processes that refuse access.
- State built once at start goes stale silently. The disk list built at a dispatcher's start missed two hot-swapped drives, and the tell was that a fresh trial disagreed with the dispatcher.

**Processes and platforms**

- A detached job is not out of reach while a live ancestor remains. Stopping the waiting process killed the job until a short-lived intermediate stood between them.
- The platform can slow a service's children without saying so. One LaunchAgent setting made every job the dispatcher started on a Mac 5 to 6 times slower per thread, and it surfaced only as flaky tests in remote runs.
- psutil's create times on the Mac move with clock corrections, and its Windows `open_files()` can wedge a process for good. A library's behaviour under long uptimes is part of the system.
- Some hangs cannot be handled from inside the process. Only a watchdog outside it, judging by a heartbeat that legitimate long passes also write, can recover.
- A fault that needs time to build up is not tested by a check right after a restart: the lost-runner bug appeared only after days, and only a simulated clock shift showed the fix working.

**A synced folder as transport**

- A synced folder is for write-once files. Records rewritten by two machines, and a heartbeat rewritten every cycle, were the pattern behind the house's sync conflicts.
- Every deleted file is a cost every peer pays for good. Rotating reports by deleting them piled up some 80,000 records; writing on change, a small separate beat and five fixed slots ended it.
- Names that are sorted as time must be in UTC.

**Testing**

- A test suite that shares files with production can change production: the keeper test restarted every dispatcher on six machines until the suite ran on a private copy.
- Clean up only what is provably abandoned. A suite that deleted every earlier scratch folder at its start broke any run still in progress; recording the owner in the folder's name made the test exact.
- Bound test writers by size, not by time. A five-second writer filled the RAM disk that Claude writes its own tool output to and stopped every session on the machine.
- A sandbox inherits whatever the process running it carries. The lease id of the suite's own lease made a test fail whenever the suite ran the way the house rule requires.
- A failure turned into "nothing" and then cached becomes permanent. Raise, cache only complete results, and retry on a bounded schedule.
- Run each new check against a control copy of the previous code, where it must fail. Independent reviews before a deploy found real defects again and again (a notice file that could stop the tick, a keeper that would have killed healthy dispatchers).

**Working with the user**

- Machine-readable interfaces beat parsing human output: splitting `whoami` on whitespace misrouted mail for any desk with a space in its name.
- Fallbacks hide where work goes. A quiet fallback to a general desk would have opened a new session for every notice under the new mail routing; stopping with a clear message is safer.
- Plan the step that needs the user's hands. Copying into another service's folder, reloading a LaunchAgent and restarting a scheduled task were each refused to the session or needed the user's yes, and each deploy waited on him.
